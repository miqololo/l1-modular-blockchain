## 1. Какую задачу мы решаем

### 1.1 Проблема

Сегодня ИИ-инференс работает в одной из двух моделей:

1. **Централизованная** (OpenAI, Anthropic, Groq): провайдер выдаёт результат, пользователь обязан ему доверять. Нет криптографических гарантий того, что инференс реально выполнен на заявленной модели, что вывод не сфальсифицирован, что параметры не подменены.
2. **TEE-аттестация** (Aleph, Phala): результат подписывается доверенным аппаратным окружением (Intel SGX, NVIDIA Confidential Computing). Это требует доверия производителю железа и ограничивает круг провайдеров.

Существуют также подходы **zkML** (Modulus Labs, EZKL), которые доказывают корректность инференса через zero-knowledge доказательства. Но zkML дорог в вычислительном плане (доказательство одного инференса 7B-модели — часы), не масштабируется на крупные модели и не позволяет провайдерам гибко выбирать рантайм.

### 1.2 Наше решение

Мы строим **оптимистичную верификацию с доказательствами мошенничества (fraud proofs)**:

- Провайдер выполняет инференс **офф-чейн** и отправляет в чейн подписанный результат с залогом.
- Открывается **окно оспаривания** (~45 секунд). В течение этого времени любой наблюдатель может перепроверить результат и подать **MsgChallenge** со своим залогом, если получил другой `output_hash` на тех же входах в той же **домене верификации** (`model, runtime, hardware, precision, tokenizer`).
- Если оспаривание подано, начинается **диспут с поручителями (vouchers)**: третьи стороны, у которых также есть сервис в этой домене, голосуют со своими залогами.
- По истечении окна резолюции чейн считает голоса. Если провайдер выиграл — оспаривающий теряет залог, провайдер получает оплату. Если провайдер проиграл — он теряет залог в пользу оспаривающего, заказчик получает возврат.

Ключевое **экономическое допущение**: для нечестного провайдера ожидаемая потеря (залог × вероятность поимки) должна превышать ожидаемую выгоду (плата × вероятность остаться непойманным). При нашем дефолте `ProviderBond = 50, Escrow = 100` это требует поимки всего **2%** случаев мошенничества — выполнимо, если в сети есть хотя бы один честный наблюдатель на каждый сервис.

### 1.3 Почему это «ОС», а не просто блокчейн

Проект называется **децентрализованной операционной системой для ИИ**, потому что в дополнение к L1-блокчейну планируется:

- **Маркетплейс сервисов** (Phase 0.5–3 — есть): любой провайдер может зарегистрировать сервис и принимать запросы на инференс.
- **Генеративные агенты** (Phase 4 — нет): композиция нескольких сервисов в составную задачу. Один агент вызывает несколько ИИ-сервисов разных провайдеров и собирает результат.
- **Расширения через CosmWasm** (Phase 5 — нет): третьи стороны могут писать свои контракты на Rust и расширять функционал маркетплейса (специализированные виды сервисов, схемы оплаты, домены верификации).
- **Аналитика и репутация** (Phase 4 — нет): дашборды по производительности провайдеров, статистика оспаривания, рейтинги доменов.

В этом смысле «ОС» = «среда, где сосуществуют сервисы, агенты, расширения и аналитика поверх общего L1». Сейчас сделан только нижний слой — сам блокчейн и маркетплейс с диспутами. Остальное — план.

## 2. Что уже сделано

Все фазы ниже отмечены **в кодовой базе**, документации, и (где применимо) в исполняемом демо. Каждая фаза имеет свои тесты и ADR (Architecture Decision Record).

### 2.1 Phase 0 — протокол и детерминизм (параллельный трек)

**Артефакты:**

- `.claude/internal/protocol/verification-protocol.md` — спецификация протокола v1 (10 разделов: угрозы, акторы, домен верификации, жизненный цикл, формат аттестации, экономическая безопасность, открытые проблемы, мэппинг спека→код).
- `.claude/internal/protocol/threat-model.md` — модель угроз с 11 проработанными атаками (A1.1 – A6.1) с разбором стоимости/прибыли/митигации.
- `.claude/internal/prior-art/` — заметки по родственным проектам: **Ora opML** (оптимистичная верификация ML на Ethereum), **Gensyn Verde** (распределённое обучение с fraud proofs), **Arbitrum Nitro** (интерактивная битсекция fraud proofs).
- `.claude/internal/adr/` — 7 ADR: монорепо, оптимистичная верификация, рантайм + домены, форма диспут-игры, экономика челленджеров, реестр доменов, sybil-устойчивость поручителей.
- **Determinism harness** (`determinism-harness/`) — независимый процесс, который перезапускает каждый инференс в своей копии домена и сравнивает хэши. Используется как ончейн-челленджер и поручитель в демо.

**Достижение детерминизма:**

`make determinism-check` запускает один и тот же промпт в двух независимых процессах `llama-server` по 3 раза каждый и сравнивает SHA-16 от вывода. На 2026-05-20: **6 одинаковых хэшей** на тапле `(TinyLlama-1.1B-Q4_K_M, llama.cpp-server, cpu-x86_64, q4_k_m)`. Это подтверждает **межпроцессный** детерминизм. Межмашинный детерминизм — задача Phase 1.

### 2.2 Phase 0.5 — vertical slice демо

Полный стек разворачивается одной командой `docker compose up -d`. Включает:

- **Чейн** (`chain/`) — кастомный Go L1 на bbolt-хранилище. Не Cosmos SDK (упростили из-за сложности компиляции в Phase 0.5), но имеет тот же шейп — модули, типизированные сообщения, события через SSE. Cosmos SDK порт — задача Phase 1.
- **Inference-node** (`inference-node/`) — Go-демон, подписывается на SSE-события чейна, при `InferenceRequested` обращается к `llama-server`, формирует аттестацию и подписанный `MsgSubmitResult`.
- **Indexer** (`indexer/`) — Go-сервис, подписывается на SSE и хранит денормализованное представление в SQLite, отдаёт REST-API для фронтенда.
- **Frontend** (`frontend/`) — Next.js + Keplr-style встроенный кошелёк. Маркетплейс сервисов, запросы, отображение статуса.
- **Determinism harness** — описан выше; в демо запускается рядом и автоматически верифицирует каждый инференс.
- **llama-server** — официальный HTTP-сервер `llama.cpp` с моделью TinyLlama 1.1B Chat Q4_K_M (~700 МБ, скачивается один раз).

### 2.3 Phase 2 — marketplace lifecycle (свёрнут в catch-up)

- `MsgUpdateService` — владелец сервиса обновляет описание/цену.
- `MsgDeactivateService` — владелец снимает сервис с обслуживания.
- `MsgDeactivateDomain` — authority выводит из эксплуатации домен верификации.
- `MsgResolveChallenge` — authority явно разрешает спор (`dismiss` или `slash`), минуя автоматический таймаут.

**Каскадная деактивация домена (Phase 3.z):** если authority деактивирует домен, чейн автоматически:
1. Деактивирует все сервисы в этой домене и возвращает их регистрационные залоги **полностью**, минуя `MinServiceLifetimeBlocks` (потому что чейн убивает сервис, а не оператор).
2. Возвращает все открытые заявки (`PENDING`, `SUBMITTED`, `CHALLENGED`) в `REFUNDED` и возвращает все залоги — заказчиков, провайдеров, оспаривающих, поручителей.

Это закрывает реальную проблему: если домен признан недетерминистичным после факта, честные пользователи не должны страдать.

### 2.4 Phase 3 — оспаривание и доказательства мошенничества

Самая нагруженная фаза. Реализована в три шага:

#### 3.x — простые bond-экономики

- `MsgChallenge` — оспаривающий ставит залог `ChallengerBondAmount` (по умолчанию 50 aios) и предъявляет альтернативный `output_hash`.
- При резолюции против провайдера: его залог идёт оспаривающему, заказчик получает возврат.
- При резолюции в пользу провайдера (`dismiss`): залог оспаривающего конфискуется.

#### 3.y — механизм поручителей (vouchers)

Решает проблему **«нечестный оспаривающий гриферит честного провайдера»**:

- `MsgVouch` — третья сторона в той же домене ставит залог `VoucherBondAmount` (25 aios) и присоединяется к стороне провайдера или оспаривающего.
- При резолюции выигравшая сторона возвращает залоги, проигравшая теряет их в общий пул.
- Из пула выплачиваются награды выигравшим поручителям.

Демо `make demo-spurious` показывает: alice подаёт нечестный челлендж против честного провайдера, determinism-harness поручается за провайдера, оспаривание отклоняется, alice теряет 50 aios, harness получает 25.

#### 3.z — устойчивость к sybil-атакам

Главная остававшаяся уязвимость 3.y: злоумышленник мог за 25 aios создать «sybil-поручителя» и перевернуть голос в любую сторону. Закрыто четырьмя шагами:

- **Шаг 1 — eligibility:** поручитель должен владеть **активным** сервисом в той же домене.
- **Шаг 2 — service-registration bond:** регистрация сервиса требует залога `ServiceRegistrationBond = 100 aios`. Возвращается только при деактивации **после** `MinServiceLifetimeBlocks = 1000` блоков (~17 минут). При ранней деактивации **конфискуется в treasury**.
- **Шаг 3 — per-domain VoucherMargin:** в домене можно настроить, насколько голоса провайдерской стороны должны превышать голоса оспаривающей. По умолчанию 0 (демо работает с одним harness), на проде >0 при наличии 2+ независимых наблюдателей.
- **Шаг 4 — VoucherBondScaleBP:** залог поручителя теперь масштабируется относительно залога провайдера в споре (`providerBond × scaleBP / 10000`). По умолчанию 5000 (50%) — численно совпадает с легаси 25/50.

Также добавлен **treasury sweep:** конфискованные залоги уходят в `ModuleTreasuryAddr`, а не накапливаются в эскроу-аккаунте. Дальнейшая судьба казны (governance, сожжение, public-goods) — задача отдельного ADR.

#### Шаг 5 — federated re-execution committee (только дизайн)

ADR-0004 зафиксировал дизайн **на будущее**: когда поручителей недостаточно (тай, отсутствие, спор о составе), эскалация идёт **не к Nitro-style битсекции** (она не работает для AI-инференса — чейн не может выполнить «один шаг» трансформера), а к **федеративному комитету повторного выполнения** — заранее зарегистрированному набору ревьюеров, которые перезапускают инференс и голосуют большинством 2/3. Реализация — задача Phase 4.

### 2.5 Phase 1 — первая часть (tokenizer pinning)

Только что (2026-05-20) добавлено:

- В тапл домена верификации добавлено поле `TokenizerID` (опциональное). Если домен фиксирует токенайзер (например, `"llama.cpp-bpe-v1"`), то аттестации провайдеров, оспаривающих и поручителей должны его декларировать; иначе чейн отклоняет с `ErrAttestationDomainMismatch`.
- Бэкпат сохранён: домены с пустым `TokenizerID` (легаси) работают как раньше — токенайзер не проверяется.
- `inference-node` и `determinism-harness` обновлены, чтобы передавать `TokenizerID` в свои аттестации.
- В демо-сид добавлено `TokenizerID: "llama.cpp-bpe-v1"`, в `docker-compose.yml` — соответствующий `TOKENIZER_ID`.

**Зачем это нужно:** разные реализации токенайзера расходятся на крайних случаях (порядок BPE-склейки, byte-fallback, специальные токены). Без пиннинга токенайзера два провайдера на одной модели могут получить разные `output_hash` на одинаковом входе — это выглядит как нечестное оспаривание, хотя оба честны. Пиннинг это блокирует.

## 3. Что предстоит сделать

### 3.1 Оставшиеся пункты Phase 1

- **Межмашинный детерминизм.** Сейчас `make determinism-check` проверяет два процесса на одной машине. Нужен второй физический хост и harness, который сравнивает результаты по сети. Это **жёсткое требование** Phase 1, после выполнения которого можно квалифицировать домен для прода.
- **Verified-runtime executor.** Сейчас inference-node вызывает `llama-server` по HTTP. Это «реальный, но неверифицированный» инференс — баннер в коде явно это говорит. Phase 1 заменяет HTTP-вызов на детерминистичный встроенный рантайм (вероятно, CGO-обёртка или Rust-биндинг к ggml). Без CGO в чейне!
- **Cosmos SDK + CometBFT.** Сейчас «консенсус» — это один Go-goroutine, который тикает раз в секунду. Это допустимо для демо, но недопустимо для тестнета: цензура транзакций тривиальна (единственный валидатор может дропнуть `MsgChallenge`). Phase 1 переносит чейн на Cosmos SDK и CometBFT, что даёт многовалидаторный консенсус и стандартные slashing-механизмы.
- **Более строгая семантика hardware_tag.** Сейчас тэг произвольный (`cpu-x86_64-tinyllama-q4`). Нужно описать, какие конкретно атрибуты CPU/GPU значимы для детерминизма (микроархитектура, версия libc, ядерные параметры), и эмпирически валидировать классы.

### 3.2 Оставшаяся часть Phase 3.z

- **Step 5 runtime implementation** — собственно реализация federated re-execution committee. Новый статус `IN_REVIEW`, новые типы сообщений `MsgEscalateDispute`/`MsgReview`, отбор ревьюеров (сначала authority-curated, потом stake-weighted), окно ревью, резолюция 2/3.
- **Withdraw из treasury** — сейчас конфискованные залоги просто копятся в `ModuleTreasuryAddr` без механизма вывода. Нужен ADR + код для governance-управляемых выплат / сжигания / финансирования общественных благ.

### 3.3 Phase 4 — публичный тестнет

- **Замена authority на multisig → governance.** Сейчас единственный dev-ключ — известная критическая централизация.
- **Generative agents** — компонента, которая позволяет декларативно описывать «многошаговый запрос» (вызов нескольких сервисов с зависимостями), и оркестратор, который раскладывает его в граф on-chain транзакций.
- **Аналитика и дашборды** — статистика по провайдерам, домены, инциденты оспаривания.
- **Rate limiting / CORS-харднинг** на публичных эндпоинтах.
- **Полный security audit** внешним аудитором.

### 3.4 Phase 5 — Celestia DA + CosmWasm

- **Celestia DA.** Перенос данных доступности на Celestia. Расширяет throughput чейна за счёт оффлоада входных/выходных URI в DA-слой.
- **CosmWasm-расширения.** Контракты на Rust, которые могут регистрировать кастомные виды сервисов (например, специализированный домен под задачи мультимодального инференса) и определять собственные схемы оплаты.

### 3.5 Внеинженерные задачи (часто забываются)

- Дизайн токеномики (валидаторский сет, стейкинг, инфляция, фи).
- Юридический анализ комбинации «маркетплейс + токен + платежи».
- Стабилизация мейннета (типично 3–6 месяцев тестнета перед мейннетом).
- Документация для интеграторов помимо текущего туториала.

### 3.6 Оценка трудоёмкости

| Горизонт | Что | Объём (2 инженера) |
|---|---|---|
| Короткий (~2 недели) | Cross-host determinism, ADR-0005 экономика, индекс service-by-owner-domain, оставшиеся мелочи 3.z | 1–2 недели |
| Средний (~2 месяца) | Verified-runtime executor, authority→multisig, observability, публичный devnet | 1–2 месяца |
| Длинный (3+ месяцев) | CometBFT-миграция, реализация committee step 5, Phase 4 agents, security audit | 3+ месяца |
| **Demo → mainnet (честная оценка)** | | **6–9 месяцев до тестнета, 12–18 до продакшена** |

Это **оценки, не план**. Реальный план — это разбивка на задачи по 1–3 дня с зависимостями. Чтобы сделать оценку планом, нужно зафиксировать конкретную цель (например, «дата запуска тестнета X») и выстроить критический путь оттуда обратно.

## 4. Используемые технологии

### 4.1 Языки

- **Go** — основной язык. Чейн, inference-node, indexer, determinism-harness. Стандартная библиотека + минимум зависимостей.
- **TypeScript + Next.js** — фронтенд. Strict mode, без `any`, тесты на Vitest.
- **Rust (будущее)** — CosmWasm-контракты в Phase 5; возможно verified-runtime executor.
- **Python (только determinism-harness вспомогательно)** — для скриптов сравнения хэшей.

### 4.2 Хранение и сериализация

- **bbolt** (Phase 0.5–3.z) — встраиваемый key-value стор, аналог LevelDB. Простое решение для демо. В Phase 1 заменится на storage Cosmos SDK.
- **SQLite** в индексере — упрощение по сравнению с Postgres из изначального плана; в Phase 4 вернётся к Postgres для масштабирования.
- **JSON canonical encoding** для подписей. Известная ловушка: порядок полей в Go-структуре имеет значение. Phase 1 заменит на proto canonical или CBOR canonical.

### 4.3 Криптография

- **Ed25519** — все подписи (транзакции, аттестации). Стандартная Go crypto/ed25519.
- **SHA-256** — хэширование (модель, вход, выход, аттестация).
- **Адреса:** `aios1` + `lowercase-hex(sha256(pubkey)[:20])`. В Phase 1 заменим на bech32 с проверкой контрольной суммы.

### 4.4 Сетевые протоколы

- **HTTP + JSON** для всех ончейн API (`/tx`, `/services`, `/requests`, etc.).
- **Server-Sent Events (SSE)** для стриминга событий чейна. Подписчики (inference-node, harness, indexer) подключаются, при обрыве переподключаются и реконсилиятся через `/requests?since=`.
- **OpenAI-совместимый HTTP API** llama-server для запросов к модели.

### 4.5 Рантайм инференса

- **llama.cpp** (HTTP-сервер `llama-server`) — реализация на C++, оптимизированная для CPU и GGUF-моделей. В демо запускается с `--threads 4 --temp 0` для жадного (детерминистичного) сэмплинга.
- **Модель:** TinyLlama 1.1B Chat v1.0 Q4_K_M (~700 МБ). Pinned по SHA-256 в `.env.example`. Маленькая, чтобы умещаться в CPU-only setup и быстро прогоняться в тестах детерминизма.

### 4.6 Инфраструктура

- **Docker + docker-compose** — оркестрация всех сервисов. Один `docker compose up -d` поднимает 7 контейнеров.
- **GitHub Actions (планируется)** — CI/CD. Сейчас тесты гоняются локально.
- **Make** — единая точка входа для команд (`make demo`, `make test`, `make ci`).

### 4.7 Фронтенд

- **Next.js 14+** с app router.
- **TailwindCSS** для стилей.
- **CosmJS-подобный** встроенный кошелёк (dev keyring, не Keplr пока что). Для демо удобно — один клик для подписи. В Phase 4 добавится Keplr/Leap.

## 5. Как запустить

### 5.1 Требования

- Docker и docker-compose (Docker Desktop / OrbStack / Colima — любой).
- Свободные **~2 ГБ RAM** для всех контейнеров.
- **~1 ГБ места на диске** (модель + образы).
- При первом запуске **~700 МБ скачивания** модели (один раз).

### 5.2 Быстрый старт

```bash
git clone <repo-url>
cd <repo-dir>
cp .env.example .env
make demo
```

Команда `make demo` делает следующее:

1. Если нет `.env`, копирует его из `.env.example`.
2. `docker compose up -d` — поднимает 7 сервисов: model-init (одноразово), llama-server, llama-server-b, chain, inference-node, determinism-harness, indexer, frontend.
3. `scripts/wait-healthy.sh` — ждёт, пока healthcheck-и пройдут (первый раз ~30–60 с из-за скачивания модели, дальше быстро).
4. `POST /demo/seed` — регистрирует домен верификации и сервис `translate-en-fr` от имени dev-ключа `bob`.
5. `POST /demo/request-inference` — alice отправляет запрос на перевод.
6. Открывается `http://localhost:3030` — фронтенд.

После этого `make poll` опрашивает статус заявки до финализации (~45 секунд из-за окна оспаривания; demo пройдёт без челленджа).

### 5.4 Что вы увидите при `make demo`

Терминал:

→ waiting for healthy services

Браузер по `http://localhost:3030`:

### 5.5 Что вы увидите при `make demo-malicious`

```
→ restarting inference-node with MALICIOUS_PROVIDER=1
→ submitting demo request (provider will fabricate output)
[4s]  latest status=SUBMITTED
[8s]  latest status=CHALLENGED         ← harness обнаружил несоответствие
[12s] latest status=CHALLENGED
[16s] latest status=SLASHED              ← по таймауту резолюции
→ harness verdicts (expect DIVERGENT + challenge_filed=true)
{
  "items": [
    {
      "request_id": 1,
      "verdict": "DIVERGENT",
      "provider_hash": "fabricated...",
      "harness_hash": "honest...",
      "challenge_filed": true
    }
  ]
}
```

Это полная демонстрация **fraud proof в действии**:
- Провайдер сфальсифицировал вывод (`MALICIOUS_PROVIDER=1` заставляет inference-node вернуть мусор).
- Harness независимо запустил инференс и получил другой хэш.
- Harness автоматически подал `MsgChallenge` с реальным хэшем.
- По истечении окна резолюции (~20 с в демо) чейн перевёл заявку в `SLASHED`: alice получила возврат, провайдер потерял залог.

### 5.6 Что вы увидите при `make demo-spurious`

Это противоположный сценарий — **защита честного провайдера от нечестного оспаривающего**:

```
→ ensuring inference-node is honest
→ submitting an honest request
[3s] SUBMITTED
→ filing spurious challenge as 'alice' (the requester)
{"ok": true}
→ wait for resolution
[4s]  CHALLENGED
[8s]  CHALLENGED          ← harness уже верифицировал, что провайдер прав, и подаёт MsgVouch
[12s] CHALLENGED
[16s] CHALLENGED
[20s] FINALIZED            ← дispute dismissed: провайдер выиграл
```

В терминах балансов:
- Alice потеряла 50 aios (залог нечестного челленджа).
- Bob (провайдер) получил 100 aios escrow + 50 залог обратно + долю награды.
- Harness получил 25 залога обратно + 25 награды за защиту правды.

## 6. Какие конкретно проблемы решены

В порядке фаз. Каждая фаза закрывает реальную атаку или класс ошибок.

### Phase 0.5

- **Проблема**: невозможно было показать «вертикальный слайс» работы — от подписи транзакции в браузере до выдачи реального инференса от настоящей модели.
- **Решение**: docker-compose демо, который запускается одной командой.
- **Что закрывает**: «как это вообще работает в принципе?» — на этот вопрос теперь есть исполняемый ответ.

### Phase 2 (свёрнут в catch-up)

- **Проблема**: владелец сервиса не мог обновить цену, отозвать сервис или удалить домен.
- **Решение**: `MsgUpdateService`, `MsgDeactivateService`, `MsgDeactivateDomain`, `MsgResolveChallenge`.
- **Что закрывает**: реалистичный lifecycle сервиса. Без этого тестнет был бы заморожен в первоначальной конфигурации.

### Phase 3.x (простые bond-экономики)

- **Проблема (атака A1.1 в threat-model)**: нечестный провайдер может вернуть мусор и заработать, если никто не оспаривает.
- **Решение**: провайдер обязан стейкать залог `ProviderBondAmount = 50` при submit. Если оспорено успешно — залог уходит оспаривающему.
- **Что закрывает**: монетарную выгоду нечестного провайдера, если хотя бы 2% случаев замечают.

### Phase 3.y (механизм поручителей)

- **Проблема (атака A2.1)**: нечестный оспаривающий может бесплатно навредить честному провайдеру, заставив его потерять залог.
- **Решение**: третьи стороны (поручители) могут вступиться за любую сторону, ставя свой залог. Если они угадали — получают награду, если нет — теряют залог. По истечении окна большинство голосов решает.
- **Что закрывает**: гриф-атаку через нечестный челлендж. Демонстрируется в `make demo-spurious`.

### Phase 3.z (sybil-устойчивость поручителей)

#### Шаг 1 — eligibility

- **Проблема (атака A3.2 в threat-model)**: за 25 aios любой кошелёк мог стать поручителем и перевернуть голос. Sybil-атака тривиальна.
- **Решение**: поручитель обязан владеть активным сервисом в той же домене. Это публичный on-chain след.
- **Что закрывает**: «бесплатный» sybil-vouching.

#### Шаг 2 — service-registration bond + active-eligibility

- **Проблема**: но регистрация сервиса была бесплатной. Sybil мог зарегистрировать пустышку, проголосовать, удалить и продолжить.
- **Решение**: регистрация сервиса требует залога `100 aios`. Возвращается только при деактивации **после** 1000 блоков (~17 минут); ранняя деактивация = конфискация в treasury. Eligibility ужесточена: должен быть **active**, не любой.
- **Что закрывает**: «дешёвый» sybil-vouching. 10 sybil-голосов теперь стоят 1000 aios в залоге, плюс время блокировки капитала.

#### Шаг 3 — per-domain VoucherMargin

- **Проблема**: в продакшене для домена с двумя независимыми наблюдателями хочется требовать не просто «провайдер не проиграл», а «провайдер строго выиграл с запасом N».
- **Решение**: при регистрации домена можно задать `VoucherMargin = 2` (например), и тогда нужно `providerVouchers - challengerVouchers ≥ 2`.
- **Что закрывает**: устойчивость к ситуации «один honest + один sybil на каждой стороне → ничья». В продакшене такие домены требуют 2+ honest watchers, что эмпирически достижимо.

#### Шаг 4 — VoucherBondScaleBP

- **Проблема**: при высоких залогах провайдера фиксированный залог поручителя становится слишком маленьким и атака на sybil-vouching снова дешевеет.
- **Решение**: залог поручителя масштабируется относительно залога провайдера: `voucherBond = providerBond × scaleBP / 10000`.
- **Что закрывает**: пропорциональность экономической безопасности поручителей размеру спора.

#### Treasury sweep

- **Проблема**: конфискованные залоги бесконтрольно копились в module escrow, мешая аудиту.
- **Решение**: отдельный `ModuleTreasuryAddr`, куда уходят конфискации. `(*State).TreasuryBalance()` показывает накопления.
- **Что закрывает**: чистоту бухгалтерии. Будущее распоряжение treasury (governance / public-goods / сожжение) — отдельный ADR.

### Каскадная деактивация домена

- **Проблема**: если authority деактивирует домен (потому что обнаружено, что рантайм недетерминистичен), все открытые заявки в этом домене раньше «застывали», заказчики не получали возврат, провайдеры не получали залоги обратно.
- **Решение**: при `MsgDeactivateDomain` чейн каскадно: (1) деактивирует все сервисы в домене и возвращает регистрационные залоги **в полном объёме** (минуя lifetime, потому что чейн убивает сервис, не оператор), (2) переводит все открытые заявки в `REFUNDED` через `executeVoidDueToDomain`, возвращая все залоги всем сторонам.
- **Что закрывает**: реальный пользовательский баг. Честные люди не должны страдать от того, что протокол признал домен сломанным.

### Phase 1 (только tokenizer pinning пока)

- **Проблема**: два провайдера, использующие одну и ту же модель, но разные реализации токенайзера (например, разные версии BPE-склейщика), получают разные `output_hash` на одном входе. Это выглядит как честное оспаривание, но это просто тихая ломка детерминизма.
- **Решение**: в тапл домена добавлено опциональное поле `TokenizerID`. Если домен фиксирует токенайзер, аттестации должны его декларировать.
- **Что закрывает**: тихую ломку детерминизма через расхождение токенайзеров.

## 9. Часто задаваемые вопросы

**Q: Это уже работает в продакшене?**
A: Нет. Это **демо** на одной машине с CPU-only маленькой моделью. До продакшена ещё ~6–9 месяцев инженерной работы (см. раздел 3).

**Q: Сколько стоит запустить?**
A: Локально — бесплатно. Нужно ~2 ГБ RAM, ~1 ГБ диска, никакого GPU.

**Q: Можно ли использовать большие модели?**
A: Сейчас pinned TinyLlama 1.1B потому что нам нужна детерминированность и быстрый прогон в тестах. В Phase 1 при переходе на verified-runtime executor можно будет добавить большие модели (Llama 3.1 8B, например), но **только если они доказали межмашинный детерминизм** на конкретном `hardware_tag`.

**Q: Почему не Cosmos SDK с самого начала?**
A: Попробовали, оказалось слишком сложно для Phase 0.5 (компиляция Ignite CLI, версия 0.50, чрезмерная для демо генерация кода). Кастомный Go-чейн с тем же шейпом был быстрее для прототипа. Cosmos SDK — задача Phase 1.

**Q: Что если провайдер использует другую модель, но утверждает, что ту же?**
A: Провайдер обязан декларировать `model_sha256` в аттестации. Если он лжёт, наблюдатели (с реальной моделью) получат другой `output_hash` и оспорят. Если провайдер согласует ложь с челленджером — это атака A3.1 в threat-model, и она не приносит прибыли (см. подробный разбор в `threat-model.md`).

**Q: А что если все наблюдатели офлайн?**
A: Это базовое допущение протокола — должен быть хотя бы один honest watcher на каждый активный сервис. Демонстрируется отказом: без harness в `make demo-malicious` нечестный провайдер бы выиграл. Operations гайд для продакшена должен включать рекомендацию запускать ≥2 независимых harness'а на каждом домене.

**Q: Почему JSON, а не Protobuf?**
A: Для Phase 0.5 проще читать в логах. Известная foot-gun: порядок полей в Go-структуре имеет значение для canonical bytes. В Phase 1 заменим на Protobuf с `deterministic = true` или CBOR canonical.

**Q: Где код для генеративных агентов?**
A: Не написан. Это Phase 4. Сейчас в монорепо есть только заглушка `agents/` (пустая), которая активируется в Phase 4.

**Q: Какую модель токеномики вы используете?**
A: Пока никакой. `aios` в коде — это просто строковое имя denom для тестового токена. Реальная токеномика (валидаторский стейкинг, инфляция, fee burn) — задача Phase 4.

**Q: Можно ли использовать CosmWasm для расширений?**
A: В Phase 5. Сейчас в монорепо есть директория `contracts/` (пустая), которая активируется в Phase 5.

**Q: Есть ли security audit?**
A: Нет. Это требование перед публичным тестнетом с реальной ценностью (Phase 4 финиш). Аудит занимает 4–8 недель календарно, бюджет ещё не выделен.

## 10. Контакты и обратная связь

Это рабочий монорепо, не финальный продукт. Если что-то непонятно или сломано:

- Откройте issue с воспроизводимым описанием.
- В коде ищите `// TODO Phase X` — это явные маркеры будущей работы.
- В `.claude/internal/PHASE.md` — текущая фаза и что предстоит.

Изменения вносятся через PR с тестами. Принципы:
- **TDD обязателен** (см. `.claude/CLAUDE.md` §4).
- **Никаких моков базы или чейна** в тестах — только реальные инстансы.
- **Никаких feature-флагов** для незавершённого функционала — используйте бранч.
- **Каждое изменение — отдельный коммит** с одной логической дельтой.

Удачной разработки. Если протокол сработает в Phase 3 (а похоже, что сработает — все формальные атаки в threat-model имеют покрытие, и `make demo-spurious` / `make demo-malicious` показывают это на практике), у нас в руках первая в мире рабочая реализация **оптимистичной верификации ИИ-инференса с поручителями и анти-sybil залогами**. Это не маленькая вещь.
